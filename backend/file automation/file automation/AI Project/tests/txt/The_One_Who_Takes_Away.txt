# Distributed Systems and Consensus

A **distributed system** is a collection of independent computers that work together and appear to users as a single system. Examples include cloud platforms, payment systems, databases, social networks, and large-scale AI infrastructure.

The difficult part is that these computers communicate over networks, and networks are unreliable. Messages can be delayed, duplicated, reordered, or completely lost. A machine can also crash while other machines continue running.

## The Core Problem

Imagine five servers storing the same important piece of data:

```text
        ┌───────────┐
        │  Client   │
        └─────┬─────┘
              │
      ┌───────┼────────┐
      ↓       ↓        ↓
   Server A Server B Server C
      │       │        │
      └───────┼────────┘
              ↓
          Server D/E
```

Suppose a client requests:

> "Change account balance from ₹10,000 to ₹8,000."

All servers need to eventually agree on the same operation. But what happens if Server B receives the request while Server C temporarily loses its network connection?

Now the system has to answer a difficult question:

**How can independent machines agree on one correct sequence of operations despite failures?**

This is the **consensus problem**.

## Consensus

Consensus is the process through which multiple nodes agree on a common value or sequence of operations.

A consensus protocol generally attempts to provide properties such as:

**Agreement:** Correct nodes should not permanently disagree about the committed result.

**Validity:** The result should come from an acceptable proposal or valid operation.

**Termination:** Nodes should eventually make progress under the protocol's assumptions.

Protocols such as **Raft** and **Paxos** are designed to solve forms of distributed consensus.

## Raft

Raft is often easier to understand than Paxos because it explicitly divides the problem into understandable roles.

A Raft cluster typically contains:

```text
Leader
  │
  ├── Follower
  ├── Follower
  ├── Follower
  └── Follower
```

The **leader** receives client operations and replicates them to followers.

Suppose the client sends:

```text
SET balance = 8000
```

The leader adds the operation to its log:

```text
Log:
1. SET balance = 9000
2. SET balance = 8500
3. SET balance = 8000
```

It then replicates the entry to other nodes.

Once a **majority** of nodes acknowledge the entry, the operation can be committed.

For five nodes:

```text
5 nodes → majority = 3
```

For seven nodes:

```text
7 nodes → majority = 4
```

This is important because the system can continue operating even if some nodes fail.

## Why Majority Matters

Suppose five servers exist:

```text
A  B  C  D  E
```

If A, B, and C agree:

```text
A ✓
B ✓
C ✓
D ✗
E ✗
```

there is a majority of three.

But if only two servers remain:

```text
A ✓
B ✓
C ✗
D ✗
E ✗
```

the cluster should normally stop committing new operations because it cannot safely establish a majority.

This sacrifices **availability** in certain failure scenarios in order to preserve consistency.

## CAP Theorem

This leads to another famous concept: the **CAP theorem**.

CAP refers to:

**Consistency (C)**
Every successful read sees the latest committed value according to the system's consistency model.

**Availability (A)**
Every request to a non-failing node receives a response.

**Partition Tolerance (P)**
The system continues operating despite network communication failures that divide nodes into separate groups.

The important insight is not simply:

> "You can only have two of the three."

A network partition can happen in a distributed system, so systems generally have to tolerate partitions. During a partition, the design often has to make trade-offs between consistency and availability.

## The Byzantine Problem

Crash failures are only one type of failure.

Imagine a malicious or malfunctioning node sends:

```text
Node A → "Value = 100"
Node B → "Value = 100"
Node C → "Value = 500"
```

Worse, it might send different values to different nodes.

This is called a **Byzantine failure**.

Systems designed to tolerate this class of failure use **Byzantine Fault Tolerance (BFT)** algorithms.

The problem becomes particularly important in:

* blockchain networks
* financial infrastructure
* aerospace systems
* security-critical distributed systems

## Distributed Transactions

Now imagine a database transaction involving two services:

```text
Bank Service
     ↓
Payment Service
     ↓
Inventory Service
```

A payment succeeds, but the inventory update fails.

You don't want:

```text
Payment = SUCCESS
Inventory = FAILED
```

while the system believes the entire transaction succeeded.

Distributed systems therefore require mechanisms for coordination, retries, idempotency, transactional messaging, compensation, or distributed transaction protocols.

One classic approach is **Two-Phase Commit (2PC)**:

```text
         Coordinator
          /       \
         /         \
      Node A      Node B
```

Phase 1:

> "Can you commit?"

Nodes respond:

```text
A → YES
B → YES
```

Phase 2:

> "Commit."

But 2PC has important weaknesses, particularly around blocking and coordinator failure.

## The Real-World Difficulty

The hardest part of distributed systems isn't simply making computers communicate.

It's dealing with uncertainty:

```text
Did the message fail?
Did the server crash?
Did the request execute but the response disappear?
Is the node slow or dead?
Did the operation execute twice?
Are two nodes working with different information?
```

For example:

```text
Client → Server
        ↓
   Operation executes
        ↓
Server crashes
        ↓
Client receives no response
```

The client doesn't know whether the operation happened.

It might retry:

```text
Retry → Server
```

Now the operation could execute twice.

This is why concepts such as **idempotency**, **unique request IDs**, **timeouts**, **retries**, **leader election**, **replication**, and **failure detection** are fundamental to distributed systems.

## Connection to Modern AI Systems

Large AI applications are themselves distributed systems.

A production AI request might travel through:

```text
User
 ↓
Load Balancer
 ↓
API Gateway
 ↓
Agent Orchestrator
 ↓
LLM Service
 ↓
Tool Service
 ├── Google Drive
 ├── Gmail
 ├── Calendar
 ├── Web Search
 └── Database
       ↓
   Vector Database
```

Now imagine thousands or millions of users simultaneously making requests.

The system must deal with:

* distributed inference
* request queues
* load balancing
* retries
* caching
* database replication
* service failures
* rate limits
* consistency
* observability
* fault tolerance

So understanding distributed systems is a major step toward understanding how **large-scale AI applications actually operate in production**.
